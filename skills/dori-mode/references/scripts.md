# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # dev dependencies only (types, tsc)
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/hc/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck
```

Needs: Bun 1.4.4+, OMP 18.18.8+, herdr or hc, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). The `command`, `file` and `url` signals need nothing extra. The full list of signal kinds is in `sessions.md`. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg`, `/proc/meminfo` (`MemAvailable` over `MemTotal`) and `df`. Memory counts as 100% free when neither source works, and swap reads as unknown on Linux.

## Configuration

`~/.dori/config.json` (or the path in `DORI_CONFIG`). Every field is optional; see `config.example.json`. `DORI_STATE_DIR`, `DORI_LEAD_PANE` and `DORI_RUNTIME` override the file.

| Field | Default | Used by |
|---|---|---|
| `runtime` | detected | every command that opens or reads a session: `"herdr"` or `"hc"`. Unset, the Dori picks hc inside an hc terminal (`HC_TERMINAL_ID`), herdr inside a herdr pane (`HERDR_PANE_ID`), else hc when it is on PATH, else herdr, and refuses only when neither is there. Lanes already open stay on the runtime that opened them |
| `stateDir` | `~/.dori/state` | registry, heavy slots |
| `laneWorkspace` | current workspace | `launch`: the herdr workspace, or on hc the `dori.group` label (default `dori`) |
| `workspaces` | all | `sync`, `dead-panes`: herdr workspaces, or `dori.group` labels on hc |
| `ignorePanes`, `leadPane` | none | sessions the sweeps skip, by id (`w1:p3` on herdr, `t7` on hc); `leadPane` is also where lanes report |
| `defaultCwd` | home | where lanes start, and the repo whose worktrees they own |
| `agentCommand`, `defaultModel`, `launchKeywords` | `omp --dori-role lane --model {model} {prompt}`, `anthropic/claude-opus-5-5`, `ulw set goal and work` | `launch`; explicit configuration remains authoritative |
| `goalMarker` | `Pursuing goal` | launch goal-check policy; OMP activity is confirmed from the trusted extension goal record, while an explicitly empty marker keeps upstream's opt-out |
| `startupWaitSeconds` | 180 | `launch`: how long after the start it waits for the agent's ready status and goal; raise it on a slow host. A value that is not a nonnegative number uses the default |
| `sessionsDir` | `~/.omp/agent/sessions` | OMP session-id lookup |
| `ompUlwPath` | `~/.dori/omp-ulw/index.ts` | role-gated extension loading; the pin is recorded in `omp-ulw.lock` |
| `nudgeAfterMin`, `postAfterMin` | 15, 20 | `freshness` |
| `closeAfterMin` | 5 | `watch` |
| `heavySlots`, `heavyMaxLoad` | 1, 80 | `heavy` |
| `deadPanePatterns` | `has stopped`, `no suitable jobs` | `dead-panes` |
| `guard` | load 150/80, 20% memory, 50 GB disk, 20 panes | `guard` |
| `hooks.threadReply`, `hooks.threadDone` | none | `freshness`, `close` |
| `hooks.transcribe` | none | `transcribe` (argv with `{file}`, prints the text) |
| `supervision` | no ceilings by default (set wallMinutes, tokens or costUsd to enable); hung after 20 min | `freshness`, `launch`, `close` (see Supervision below) |
| `repoIdentities` | none | `verify-pr`, `launch` footer: expected Git name and email per `owner/repo` (keys match without case) |

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

## Library modules

The CLI is a thin layer over typed modules you can import in your own scripts:

| Module | What it gives you |
|---|---|
| `src/messenger/slack.ts` | `Slack`: post, edit, thread replies, file upload (upload URL + complete), presence; 429 backoff |
| `src/messenger/telegram.ts` | `Telegram`: send, edit, typing, `sendMessageDraft` streaming with a `Thinking…` start, forum topics (create, rename, close, reopen), HTML tables |
| `src/messenger/discord.ts` | `Discord`: send without pings, edit, typing, threads (start, rename, archive); gateway presence |
| `src/messenger/typing.ts` | `typingWhile`: show typing while a piece of work runs, stop when it ends |
| `src/messenger/voice.ts` | `transcribe`: voice note to text through your hook |
| `src/messenger/thread-ledger.ts` | `ThreadLedger`: every thread the Dori posts in, persisted; given to `Slack`, it records each `chat.postMessage` (also raw `call`s) |
| `src/messenger/slack-inbound.ts` | `pollSlackInbound`: threads view, the ledger's threads and unread counts, deduplicated, own messages filtered |
| `src/messenger/telegram-inbound.ts` | `pollTelegramInbound`: owner-gated `getUpdates` long-poll, persisted offset, DMs and the group gate |
| `src/messenger/slack-presence.ts` | `slackPresence`: hold a user account active |
| `src/routing.ts` | `canLaunch`, `idleLaneFor`: the routing checks |

Every module takes its HTTP, clock and timers as arguments. That is how the tests run without the network.

## Commands

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--model M] [--cwd DIR] [--dry-run]`
Opens a lane: puts current global and repository lessons above the brief, appends the footer, creates the runtime session and starts OMP. After 20 seconds it checks the unwrapped screen for known startup failures, including OMP extension/flag/model errors. Provider failure phrases are distinguished from code, paths and lane names; a custom omo agent's recoverable missing-extension warning is ignored, but a real failure beside it still counts. `STARTUP_OK` requires idle/working runtime status and an active goal from the live-process-bound OMP extension record; goal state is independent of terminal width, and an approval or shell never counts as ready. Custom agents retain their own goal record or footer-marker check. An explicitly empty `goalMarker` opts out of the goal check, not readiness. The status and goal are rechecked every 10 seconds until `startupWaitSeconds` (180 by default) after start, including while an agent has not reported a status yet. A running agent without a confirmed goal reports `STARTUP_NO_GOAL`; missing readiness is `STARTUP_UNCONFIRMED`. Lookup errors, shells and known failures end the wait immediately. A gone session whose lane is already closed, verified-done or journal-done is `STARTUP_DONE <key>`. Exit 0 on `STARTUP_OK` or `STARTUP_DONE`, and 3 otherwise.

The lane never gets the Slack token itself: on hc every env value is a command-line argument, which `ps`, `hc get` and logs show. When the launcher has `DORI_SLACK_TOKEN_FILE`, or a `slack-token` file sits next to its config, the lane gets that path as `DORI_SLACK_TOKEN_FILE` and an empty `DORI_SLACK_TOKEN`, so a token inherited from another home's core cannot win. The path is passed absolute. A `DORI_SLACK_TOKEN_FILE` outside the launcher's home (its config's directory) is most likely inherited from another home, so the launch refuses it (`token file refused: ...`) unless `DORI_SLACK_TOKEN_FILE_OUTSIDE_HOME=1` says it is meant; links are resolved first, and the flag is passed to the lane empty. `dori boot` refuses such a path the same way. With neither, the lane env is unchanged.

`--dry-run` prints the brief as the lane would get it, lessons and footer included, and changes nothing.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF]`
Registers a lane that is already running.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by drift. Read-only unless `--write`, which stores session ids.

### `dori report <key> --kind milestone|blocker|question|halted|done --text TEXT`
Run by a lane. Appends one record to `<stateDir>/lanes/<key>/reports.jsonl` and prints the `[REPORT] <key> | <kind> | <text>` line the lane then sends to the lead pane. Each record is a single append, so the lane and the lead can write at the same time without losing one. The last record is the lane's progress state: `milestone` is running, `blocker` and `question` blocked (a question waits on the owner's answer), `halted` halted, `done` done. The screen grammar takes the same five kinds. Text stays data: newlines are folded into the printed line, never into the journal. A corrupt journal is an error with its line number, never an empty state. Lanes opened by `dori launch` are told to report this way and are marked `reportProtocol: "jsonl-v1"`; launch starts their journal with a `running` activity record, which is not a report and is never posted.

### `dori boot`
Run by the lead after a restart or a compaction, before it trusts what it remembers. It is read-only: it writes no registry record, relaunches nothing and stops no watch. It prints:
- `RUNTIME <kind> (from <source>)` first: the runtime new lanes open on and why (`env`, `config`, `detect:HC_TERMINAL_ID`, `detect:HERDR_PANE_ID`, `detect:path`). `RUNTIME unavailable: <fix>` when none can be chosen, and boot then exits non-zero.
- `SLACK authenticated user=... team=...` from `auth.test` when `DORI_SLACK_TOKEN` is set or `DORI_SLACK_TOKEN_FILE` names a token file (`SLACK skipped` otherwise). A token file that is missing, unreadable, not a regular file, owned by another user, empty or open to group or others is `SLACK token-file: <reason>`, naming only the path, and fails the boot. This proves the token, not that messages arrive. It runs last, after the local checks below, and gives up after 10 seconds (`SLACK auth.test timed out after 10000 ms`). A response without a user or team id is `SLACK auth failed`.
- `PANES` with the lead pane's state, then `VANISHED <key> pane=...` for each open lane whose pane is gone (a `verified-done` lane is not flagged), and `UNREGISTERED <panes>` for panes no lane owns. Sessions are listed on every runtime a lane lives on (`herdr pane list` / `hc ls`); if that list fails, no lane is called vanished.
- `DRIFT n=<count> <keys>`: lanes not finished (`closed`, `verified-done`, or a `done` report, the lanes `VANISHED` skips too) whose session the runtime's own probe reports gone (`herdr pane get`, `hc get`). Only lanes missing from the session list are probed. Any drift fails the boot; a probe that errors is `DRIFT probe-failed <key> (...)` and also fails it.
- `CONFIG_WARN workspaces=[...] does not include laneWorkspace=...` when `config.workspaces` is set and leaves out `laneWorkspace`, or `CONFIG_WARN workspaces=[...] match none of the <n> live agent sessions ...` when live agent sessions (in `laneWorkspace` when it is set, the lead and `ignorePanes` aside) exist and none is in `config.workspaces`: `dead-panes` and `sync` filter on that list and would watch nothing. Checked only on a runtime with workspaces (herdr; hc has none). It fails the boot.
- `REPORT <key> kind=... at=... state=...` for each launched (`jsonl-v1`) lane's last report, next to its registry status, since the two can disagree after a crash. A journal that holds only records dori wrote itself (the launch, a screen-detected stall) is `NO-REPORT <key>`, never a report, and a launched lane with no `reports.jsonl` yet is `NO-REPORT <key> ... (no journal)`. An adopted lane's journal is not read, as in `freshness`. An unreadable journal is `JOURNAL-ERROR <key>: ...` for that lane only; the other lanes are still checked.
- `WORKLOG open=<n>` and an `OPEN <id> "<title>" source="<ref>" next="..."` line for each open worklog item (see `dori worklog` below).
- `CLEANUP <keys> match=...` and an owner-session-only stop command for persistent watches tied only to finished lanes (closed, verified done, or a `done` report). OMP manifests are read from `<stateDir>/monitors/<encoded session id>.json`; exact argv tokens tie a watch to a lane, and any mention of an open lane keeps it. OMP cleanup uses `monitor({"op":"stop","name":...})` in the owning session. Original terminal-manifest discovery and its `kill_bash(...)` recommendation remain available for that metadata format. Boot never opens private session transcripts or stops a watch. Expired terminal watches remain `EXPIRED` with nothing to stop, and unreadable metadata remains an explicit `MONITORS unreadable` error.

Exit 0 ends with `BOOT checked`. A lane file that cannot be read or parsed, or a lanes path that cannot be listed, is `REGISTRY unreadable <path>`; the other lanes are still checked. Any input that could not be read (Slack, the registry, panes, a journal, the worklog, metadata) is printed and gives `BOOT incomplete`, exit 1.

### `dori checkpoint <key> --step ID --result TEXT --evidence PATH [--remote-effect RECEIPT]...` / `dori checkpoints <key>`
Run by a lane after each completed step, and on resume before doing work. Each step is one line in `<stateDir>/lanes/<key>/checkpoints.jsonl` with its result, evidence and the receipts of remote effects it completed (a push, a merge, a deploy). Recording the same step again with the same data returns the original, unchanged; different data for a recorded step is refused, and so is a receipt another step already recorded. Writes fsync the journal (and its directory when they create it) under a lock file, `checkpoints.jsonl.lock`, that records the writer's pid, host and time. A live writer's lock is refused with its pid and age. A lock whose pid is dead on this host, or that is two minutes old, is taken over, so a writer killed mid-write never locks the lane.

A lane reads its checkpoints before resuming and never repeats a recorded remote effect. A crash between a remote action and its checkpoint is not covered by the journal: read the live remote state first, and use the service's idempotency key where it has one.

### `dori verify-pr <owner/repo> <num> [--loop N] [--cwd DIR]`
Run before a lane claims PR work done. It reads the PR through `gh api` (the PR, every commit with all of its files, the PR's files, then the PR again) and checks:
- every commit's author and committer email is the one in `repoIdentities` for that repo, ignoring case. The name may differ. `noreply@github.com` is accepted only as the committer of a merge commit, even if it is the configured email. A repo with no configured identity fails before anything is read; `loadConfig` drops an entry whose `name` or `email` is not a nonempty string, so such a repo counts as unconfigured;
- a PR with `fix:` or `fix(<scope>):` commits (with or without `!`) that touch source changes at least one test. A test file counts when GitHub lists it as added, modified, renamed, copied or changed (not removed) and it is named as a test (`*.test.*`, `*.spec.*`, `test_*.py`, `*_test.go`, `*_test.py`) or sits in a `test`, `tests` or `__tests__` directory. Nothing under a `fixtures`, `__fixtures__`, `__snapshots__`, `helpers`, `fakes` or `mocks` directory counts. In a test directory, a file that is not named as a test does not count when its name is `setup`, `conftest`, `test-utils`, `fixture(s)`, `helper(s)`, `fake(s)` or `mock(s)`, or when it sits in a `setup`, `conftest` or `test-utils` directory; a file named as a test (`test/setup.test.ts`, `test/helpers.test.ts`) counts. A body line `No test: <reason>` waives this. A fix commit without its own test is a warning, since its test may be in a later commit.

If the head, body or commit count changed between the two reads, or GitHub's answer is incomplete, the result is `FAIL`. Each `gh api` call is killed after 120 seconds, which is also a `FAIL`. Changed UI tests (`.tsx`/`.jsx`, a `ui`, `component(s)`, `feature(s)`, `e2e`, `browser` or `playwright` directory, or DOM calls in the patch) are listed with a shell loop that runs them `--loop` times (default 20) at the reported head. dori never runs the loop. `PASS` exits 0, `FAIL` exits 2.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered.

### `dori close <key> [--note TEXT]`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live. On success it marks the thread done through `hooks.threadDone`, closes the tab, and removes the lane's worktrees with a plain `git worktree remove`, which refuses a dirty worktree.

### `dori lesson add <key> --rule TEXT --evidence PATH [--cwd DIR]` / `lesson add --global --rule TEXT --evidence REF` / `lesson list [--cwd DIR]` / `lesson mark <id> --outcome ...`
A lesson is one rule learned in a lane, tied to the evidence that taught it and to the lane's repo (its `cwd`, resolved to a real path). A `--global` lesson is the lead's standing rule for every lane, whatever its repo: it has no `cwd` and is recorded as `lane: "lead"`. Since it reaches every future brief, it is the lead's: `--global` with a lane key is refused and writes nothing. So are `--global` and `lesson mark` on a global lesson when run from a pane that a registered open lane owns (your own session, from `HC_TERMINAL_ID`, else `HERDR_PANE_ID`, found as `claim-done` finds its lane); repo lessons stay markable from lanes. The pane check is a convenience check that stops a lane from adding or reviving a global lesson by accident or on routine instruction. It is not a security boundary: it reads only the session variables (`HC_TERMINAL_ID` first, then `HERDR_PANE_ID`), so unsetting them gets past it, and anything that can write files can append to `lessons.jsonl` directly. `dori launch` puts the newest `pending` or `helped` lessons for the new lane above its brief: up to 4 global ones under "Lessons for every lane", then up to 8 for its `cwd` under "Lessons for this repo". Each kind has its own cap, so global rules never push repo lessons out. `lesson list --cwd DIR` shows the global lessons too. `mark` records whether a lesson `helped`, had `no-effect`, was `harmful`, or is now `encoded` in a test, lint or doc; only `pending` and `helped` reach new briefs. Lessons live in `<stateDir>/lessons.jsonl`, one record per change: a mark appends, it never rewrites history. A rule is one line of at most 400 characters. A damaged line (not JSON, an unknown field, a malformed field, or a change to a lesson's fixed fields) is skipped and named: `lesson list` and `launch` print `LESSON_WARNING <path>:<line>: <reason>` on stderr and go on with the other lessons. The reason names the field for a malformed, unknown or changed field; a line that is not JSON, or not a JSON object, has no field to name and is reported as such. Each record starts on its own line, so a write cut off halfway damages only its own line.

`dori close <key> --lesson TEXT [--evidence PATH]` adds a lesson as part of the close (evidence defaults to the `Done =` line). It never blocks the close: a failure prints `LESSON_WARNING`.

### `dori worklog add <title> --source REF` / `next <id> <text>` / `note <id> <text>` / `close <id> --result TEXT` / `list [--open]`
The lead's record of owner requests, so an open request survives a restart, a compaction or a handoff. `add` records a request when it arrives, with its source (`slack:<channel>/<ts>` or any reference to the message) and prints the item with its 8-hex-digit id. `next` replaces the item's next step, `note` adds a dated note (a decision, who owns it), `close` records the result and ends the item; a closed or unknown item is refused. Each text is one line, without control characters (C0, DEL, C1) or the Unicode line and paragraph separators. `list` prints the items as JSON (`--open` only the open ones), oldest first.

The record is `<stateDir>/worklog.jsonl`, one append per change, so the lead and a lane can write at the same time without losing one; a write cut off halfway damages only its own line, which every reader skips quietly as a normal result of the design (a line that does not parse but begins like a record, `{"op":"`). Any other bad line is real damage: `list` names it as `WORKLOG_WARNING <path>:<line>: <reason>` and skips it. If two writers close the same item at once, the first close in the record wins and a later `close` is a no-op; a `next` or `note` after the close lost the same race: it is skipped and `list` still names it as a `WORKLOG_WARNING`. After every change `<stateDir>/worklog.md` is rendered from the whole record (temp file and rename) for the lead to read: one heading per item with Source, Opened, Next, Notes and, once closed, Closed and Result, open items first. A render that raced another writer's append renders again, so the file always ends up holding every item. Edit through the command, not the file: a `worklog.md` that the command did not write (no marker on its first line) is never replaced (the marker is checked before the append and again right before the rename, and a publish that finds it gone is skipped), and every change is refused until it is moved aside.

`dori boot` prints `WORKLOG open=<n>` and one `OPEN <id> "<title>" source="<ref>" next="<next step>"` line per open item, so the lead continues each from its Next line. A damaged line (not a torn write, a duplicate close, or a `next`/`note` after a close) is `WORKLOG damaged <path>:<line>: <reason>` and makes the boot incomplete. A `next` or `note` after a close prints as `WORKLOG warning <path>:<line>: <reason>` and does not fail the boot.

### `dori pause <key> [--note TEXT]` / `dori resume <key> [--note TEXT]`
`pause` is for when the owner said wait. It works on a `working` or `not-done` lane. It sends `/goal pause`, then confirms the current OMP session's recorded goal is paused or absent before marking the lane paused and sending Escape to an active turn. A completed/dropped goal requires the corresponding OMP no-goal screen response as corroboration. Missing/stale state, an open approval, or an unconfirmed send leaves the lane unchanged with `PAUSE_UNVERIFIED`, exit 3. Pausing the goal first prevents Escape from triggering a continuation.

A paused lane is skipped by `freshness`: no nudge, no post. Only `dori resume` ends a pause, on the owner's word. Activity never does, because a paused lane can still be woken by a background result, a queued message or a turn after Escape. If its pane reads `working` on two ticks in a row, `freshness` prints `WORKING-WHILE-PAUSED` once per working stretch (again after it goes idle and is woken, or after a new pause), so the lead can ask the owner, and the lane stays paused.

`resume` sends `/goal resume` and confirms the trusted OMP goal state is active, then restores the lane's `pausedFrom` status and resets quiet time so a long pause does not become an instant nudge. Missing/stale state, an approval hold or an unconfirmed send gives `RESUME_UNVERIFIED`, exit 3.

Both print `PAUSED` / `RESUMED` and exit 0 on success. A lane in any other state is refused (`NOT_PAUSED` / `NOT_RESUMED`, exit 2), and a second `pause` is a no-op. `claim-done` and `object-done` on a paused lane move it out of `paused` in the registry while its goal stays paused.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The deadline lives in the registry, so a restart picks up where it left off.

### `dori freshness [--loop MIN]`
For working lanes that have gone quiet: a nudge in the pane after `nudgeAfterMin`, then the lane's last `[REPORT]` line posted to its thread after `postAfterMin`, with home paths and pane ids scrubbed. Each happens once per silence. The line is posted only once it is still the last `[REPORT]` line on the next tick (`PENDING-REPORT` the first time) and differs from the line posted last time (`STALE-REPORT` otherwise). A `[REPORT]` line counts when it starts the row or is a whole quoted element of an argv array, the shape lanes send it in (`["herdr", "pane", "run", "<lead pane>", "[REPORT] key | kind | text"]`, or `["hc", "send", "<lead terminal>", "--", "[REPORT] key | kind | text"]` on hc). Prose that quotes the grammar mid-sentence, and a report whose text is one unfilled placeholder, are not reports. A held-back outcome is printed once per change, not on every tick. A nudge reports its delivery as `delivered` (the agent status moved to working) or `unconfirmed`.

A lane with a `reports.jsonl` journal is read from the journal first. Its last report skips the two-tick `PENDING-REPORT` wait, since it cannot scroll off, and is posted once the thread has had no update for `postAfterMin`, so a lane that reports often still has its latest report posted, at most once per `postAfterMin`. Its time counts as the lane last being heard from, so a fresh report suppresses the nudge. A `blocker`, `question`, `halted` or `done` lane is not nudged, but its report is still posted. A `stalled` lane is neither nudged nor posted: it stopped on a failed compaction or at an idle prompt, so a typed nudge cannot restart it and a person has to look. `STALLED` is printed once per stall for the monitor (see the filter in `setup.md`), and `Working` on the screen returns the lane to running, after which nudges and posts resume. A `jsonl-v1` lane never falls back to scraping the screen. `launch` starts its journal with a `running` activity record, which is not a report, so a lane with no report of its own is `NO-REPORT` and is still watched for a stall; a `jsonl-v1` lane with no journal at all is `NO-REPORT` and is not watched. The screen is still read for activity: a compaction failure with no `Working` line below it, or an idle prompt with no `Working` line and no report for `nudgeAfterMin`, marks the lane `stalled` and prints `STALLED` once; `Working` on the screen moves it back to running. A journal that does not parse skips its lane and prints `JOURNAL-ERROR` with the file and line, once per error; the other lanes are still swept. Adopted lanes ignore the journal and keep the screen path. On the screen, a report is a line that starts with `[REPORT]` (after indentation) or the last quoted element of an argv row such as `["herdr", "pane", "run", "lead:p1", "[REPORT] ..."]`, optionally inside one spawn call. Prose, an instruction or a prompt that quotes the grammar mid-sentence is dropped.

#### Supervision
For launched (`jsonl-v1`) lanes whose `reports.jsonl` journal exists, each `freshness` tick also checks the items below. An adopted lane is not supervised: it has no ceilings and no hung-call check, even if a journal exists for its key.
- **Ceilings.** `wallMinutes` since the lane opened, and `tokens` and `costUsd` from `supervision.usageArgv`. Reaching one appends a `blocker` report and prints `BLOCKED`. The lane is never killed, closed or sent anything; it waits for the lead, and raising a ceiling alone does not resume it. Limits come from `supervision.defaults`, then `supervision.lanes.<key>`, then `launch --wall-minutes N|none --token-limit N|none --cost-limit N|none`, and are saved on the lane. `null` (`none`) disables one. A malformed `supervision` entry (a ceiling that is not a nonnegative number or `null`, a ceiling or setting name that does not exist, such as `toknes`, a `lanes` entry that is not an object, an argv or path list that is not strings) stops every command with `invalid supervision <name>`, so a typo never turns a ceiling off.
- **Hung calls.** A `Working` or `Running` timer on the screen that keeps growing from the same start for `hungAfterMinutes`, with no new report, checkpoint or file change for `staleAfterMinutes`, marks the lane stalled (`STALLED`). File changes are git's changed-file list in the lane's `cwd` (`gitActivity`), leaving out `node_modules` and paths outside `cwd`, plus `activityPaths` and `launch --activity-path FILE`; directories are not walked.
- **Usage.** `supervision.usageArgv` is an argv template (`{key}`, `{session}`, `{cwd}`) that prints `{"tokens": N, "costUsd": N}` cumulative totals. Missing or malformed values are unknown, never zero, and a ceiling that cannot be checked prints `WARNING` once. With `usageArgv` set, each reading is appended to the lane's `cost.jsonl`; without it, sweeps record nothing.

Each alert prints once per change. `close` takes one more usage reading, prints `COST <key> tokens=... costUsd=...`, and, when either is known, runs `supervision.recordCostArgv` (`{key}`, `{session}`, `{tokens}`, `{costUsd}`, `{at}`, and `{closeKey}`, `<key>@<openedAt>`, the same on every attempt; unknown values are the literal `null`). Once the hook succeeds the reading is marked final in `cost.jsonl`, and a later close of the same lane returns it without running the hook again. If that hook fails, close prints `COST <key> not recorded: <reason>` and still closes the lane. A supervision step that fails (an unreadable `supervision.json` or checkpoint journal) prints `SUPERVISION-ERROR <key> <reason>` once per reason; that lane's reports are still read and posted, and the other lanes are still checked. Both hooks run without a shell and time out after 10 seconds. Run one `freshness` sweeper for all lanes: each tick covers every open lane, so a second sweeper would repeat nudges, thread posts and supervision alerts.

### `dori dead-panes [--loop MIN]`
Prints `DEAD_PANE <id>` once per hour for a pane with no running agent status whose last lines match `deadPanePatterns` on two ticks in a row with the same text. A pane the runtime reports as idle, working, blocked or done (on hc: the agent's own report, which can also be error) is never dead. A pane that is neither is unrecognised; three unrecognised ticks in a row print `UNRECOGNISED_PANE <id> ...` once (list non-agent panes in `ignorePanes`).

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed.

### `dori can-launch`
Prints `CAN_LAUNCH` and exits 0 when the host has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. The reasons come from the guard's memory, disk and pane-count thresholds. CPU load alone never holds a launch, because it moves too fast to plan around.


### `dori usage omp --session ID`
Reads the OMP session file for `ID` from `config.sessionsDir` (default `~/.omp/agent/sessions`). Looks for `*_<ID>.jsonl` under any subdirectory. Sums `totalTokens` and `cost.total` from:
- `type=message` entries where `message.role` is `"assistant"` → `message.usage.totalTokens` and `message.usage.cost.total`
- `type=model_usage` entries → `usage.totalTokens` and `usage.cost.total`

Prints one JSON line: `{"tokens":N,"costUsd":X}`. A session not found or unreadable file exits nonzero (supervision treats unknown usage as unknown, never zero). A torn last line (incomplete write from a crash) is skipped; other lines are still summed.

Wire it as the supervision usage reader:
```json
"supervision": {
  "usageArgv": ["dori", "usage", "omp", "--session", "{session}"]
}
```
The `{session}` placeholder is filled with the lane's OMP session id. This makes `supervision.usageArgv` report live token and cost totals for OMP lane ceilings and the `COST` line on close.

### `dori send <slack|telegram|discord> --to TARGET --text TEXT [--thread ID] [--edit ID]`
Posts a message, or edits one with `--edit`. Tokens come from `DORI_SLACK_TOKEN`, or when that is unset or empty from the file `DORI_SLACK_TOKEN_FILE` names (plus `DORI_SLACK_COOKIE` for a user token). The file must be a regular file you own and owner-only (`chmod 600`), checked and read through one open descriptor; a file open to group or others, owned by someone else, not a regular file (a FIFO never blocks the read), missing or empty is refused. Windows has no mode bits or uid to check, so there the file's ACL is the owner's to set, and `dori boot` prints `SLACK token-file: the token file's NTFS ACL is not checked on Windows; ...` as a reminder. Other tokens come from `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`. Text containing `$(` is refused, since it can only come from a shell string. Rate limits are retried with the server's wait time; other errors fail at once.

### `dori presence <slack|discord>`
Keeps the account shown as online until explicitly stopped. Enable one instance per account under the owning OMP session's native `monitor` tool; two writers can compete.
- **Discord:** use your own `DORI_DISCORD_TOKEN` in the child environment. REST inbound polling and message sending do not establish online presence. The Gateway keeper emits `PRESENCE_READY discord event=READY|RESUMED` only after that real dispatch, `PRESENCE_ACK discord seq=<number|->` only for the first actual heartbeat acknowledgement per connection and `PRESENCE_RECONNECT` while reconnecting. Later routine acknowledgements update lifecycle state silently. Authentication/configuration/intent failures exit nonzero with sanitized errors. SIGINT/SIGTERM ends retries, sockets and timers with `PRESENCE_STOPPED discord`; intentional monitor stop means offline. Restart only by explicit choice. See [operational details](../../../docs/releases.md#discord-online-presence).
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes. This retained source feature is outside the first Discord preview's live support scope.

### `dori inbound discord [--loop MINUTES]`
The supported Discord text intake is built into Dori and uses the owner's bot token directly. It needs no Node, agent-messenger CLI, SDK adapter or private helper. Required child environment: `DORI_DISCORD_TOKEN`, `DORI_DISCORD_OWNER_ID`, `DORI_DISCORD_CHANNEL_ID`. The two IDs are positive decimal snowflake strings, never JavaScript numbers.

Without `--loop`, it polls continuously every three seconds. `--loop 0.1` is six seconds; `--loop 0` is one-shot. Startup validates the authenticated bot, application Message Content Intent, channel access and View Channel/Read Message History permissions before printing `INBOUND_READY discord owner=<id> channel=<id> bot=<id>`. Sending replies additionally needs the relevant send/thread permissions.

On first start, the latest message ID is atomically saved without replaying history; an empty channel saves `0`. Send the first new request after readiness. The committed cursor is retained at `<stateDir>/discord-inbound/<channelId>.json`, in an owned private directory with atomic mode-0600 cursor files. Resumed polling pages back to that cursor, deduplicates messages and emits owner text chronologically. Successfully handled items advance the cursor.

Output is `INBOUND discord <channel> <message> from=owner ref=<id|-> <JSON text>`. Bots, self, non-owner, webhook and system messages do not emit owner intake. Only the exact configured channel is read; a thread requires its own channel ID. This is new-message text polling, not guild-wide/thread discovery or a general edit/delete/media event stream.

Use one opted-in native `monitor` with filter `^INBOUND` and the [protected-token child argv recipe](../../../docs/releases.md#discord-owner-intake). Startup auth, permission, intent or state failures are sanitized nonzero errors; later failed polls follow the ordinary `WARN`/retry loop. SIGINT/SIGTERM stops intake, and an explicit restart resumes the committed cursor. REST polling never changes Gateway presence; enable or stop the separate presence monitor intentionally.

### `dori inbound slack [--loop MIN]`
Prints `INBOUND <source> <channel> <thread> <ts> <user> <text>`. It reads from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found.

### `dori inbound telegram [--loop MIN]`
Prints `INBOUND <source> <chat> <thread> <update-id> mid=<message_id> <from> <text>[ file=<kind>:<file_id>]`, keeping Slack's field order — `source` is `dm`, `topic`, `edit:dm` or `edit:topic`. `mid=<message_id>` is always present (never optional, so later fields never shift; `-` when unknown) and names the Telegram message behind the line: a new message and the edits that replace it share the same `mid=`, so a consumer can pair an edit with the original line. A media message appends ` file=<kind>:<file_id>` (voice, audio, video, video_note, animation, document, photo); the line carries the `file_id`, which a caller can pass to Telegram's `getFile`. Live-location shares arrive as a stream of edits carrying only coordinates — those are dropped, not one line each. The corrupt-offset WARN prints to stdout, like every other inbound WARN. Without `--loop` the command is exactly one poll and returns, productive or not. Long-polls `getUpdates`:
- only the configured owner's messages pass (`DORI_TELEGRAM_OWNER_ID`); bot messages never do;
- DMs from the owner always pass; in a group (`DORI_TELEGRAM_GROUP_ID`) only the configured topic (`DORI_TELEGRAM_TOPIC_ID`) does — with a group but no topic, every owner message in the group passes — with no group configured, DMs only;
- delivery is at-least-once: the offset in `<stateDir>/telegram-offset` advances past a message only after its `INBOUND` line is out (dropped updates advance immediately), so a crash replays at worst the unprinted lines — duplicates carry the same update id;
- the full text is printed, JSON-escaped on one line: `getUpdates` cannot fetch a message again;
- edits arrive too: `edited_message` updates are polled and printed as their own `edit` kind, carrying the edited text;
- env ids are validated at start — `DORI_TELEGRAM_OWNER_ID`, `DORI_TELEGRAM_GROUP_ID` and `DORI_TELEGRAM_TOPIC_ID` must match `/^-?\d+$/` after trimming; empty, whitespace-only, `1e3` and `0x10` are refused with an error naming the variable;
- reuses the bot token the skill already stores (`DORI_TELEGRAM_TOKEN`).

### `dori transcribe <audio-file>`
Runs `hooks.transcribe` and prints the transcript. A failed or empty transcription is an error, never an empty message.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.

## Complete harness entrypoint

`dori harness <args...>` dispatches to the retained upstream harness in `src/cli.ts`. It supports `up`, `role`, `start`, `report`, `ready`, `send`, `inbox`, `duty`, `review`, `merge`, `done`, `status`, `loop`, `backlog` and `migrate` without taking over the primary messenger/lane `dori` namespace. Direct source invocation is `bun src/cli.ts <args...>`; a separately linked root package exposes `dori-harness`. Nothing in installation starts this harness or another production messenger.

## Consumer release management

`dori --version` and `dori update <check|install|status|rollback> [--version TAG] [--from DIST]` dispatch before normal Dori config loading. `check` and `install` accept an exact tag or a verified local asset directory; without a tag, network selection is stable-only. `rollback` validates the retained previous source and optionally asserts its tag with `--version`; `status` and `rollback` do not accept `--from`. Local Dori assets do not eliminate the initial anonymous network fetch for pinned public omp-ulw when it is not already provisioned.

These consumer commands use no porting/review models or GitHub write permission. Install/update/rollback activation holds while any live Dori is detected, including idle sessions; operators explicitly stop their own monitors and end the owning session before retrying. No implicit kill, restart or watcher restoration occurs. Existing config/auth/work/sessions remain intact. Follow the [release guide](../../../docs/releases.md) for canonical download identity, checksum/source verification, interrupted-activation recovery and support limits.

## Staged Dori updates

`dori upstream` is the maintainer source-porting interface, with its own required `--config FILE`, dispatched before normal Dori config/state loading. It is separate from consumer `dori update`. Without `promotion`, it only stages source candidates and never commits, pushes or replaces live Dori. An explicit owner-approved promotion policy enables exact-source publication and optional managed herdr replacement after all checks and fresh review pass. That policy is standing authorization for its configured target, not permission for arbitrary repositories or sessions. Installation and boot never enable it. Neither mode upgrades global Bun, changes global model policy or updates ULW.

The complete example is [`examples/update.config.json`](../../../examples/update.config.json), relative to the repository root. Its paths resolve relative to that file: it reads this checkout as `localSource` and writes an independent sibling staging directory. It requires Bun 1.4.4+, Git, actual OMP on PATH, the configured model/provider capability and the configured verification tools. Edit explicit model/thinking selectors to match the operator's worker and reviewer policy; these are example command arguments, not model defaults in the controller.

The native agent route targets the observed OMP 18.18.8 CLI/protocol. Both agents use `--no-pty`; the reviewer additionally uses `--no-lsp` to disable LSP tools, formatting and diagnostics, while the worker retains normal navigation support. User-supplied `--dori-role`/extension/profile flags are rejected. The controller loads its own trusted guard with an explicit `-e` for each agent (reviewer: exact read-only set; worker: built-in search/edit/shell tools only); normal role sessions and their pinned extension behavior remain unchanged.

Agent commands may declare `engine:"omp"` or `engine:"external"`. Use `"omp"` for an arbitrary actual compiled CLI path/argv so native final-message parsing and the capability guards are always applied. Without it, the existing OMP executable/installed-entrypoint detector reads the argv template. A native OMP argv must end with the `{prompt}` positional; the controller inserts its isolation options immediately before it (and before a `--` placed right before it), and rejects resume/continue/restore/fork flags. `"external"` is an explicitly trusted wrapper contract: the wrapper must run a real fresh model context, enforce read-only review itself, and return only the final structured verdict line. No external wrapper or model command is supplied as a fake default. Whatever approval policy the CLI needs for edit/write/bash in print mode must be part of the configured worker argv; the controller never adds auto-approval.

Before either native worker or reviewer starts, the job-owned `--config` overlay sets `disabledProviders` to `native`, `mcp-json`, `omp-plugins`, `agent-plugins`, `claude`, `claude-plugins`, `codex`, `gemini`, `opencode`, `cursor`, `windsurf`, and `vscode`, and preserves `mcp.enableProjectConfig:false`. OMP 18.18.8 loads this overlay before binding discovery settings and loading MCP, disabling every MCP-capable discovery source before server startup and instruction injection. This uses the supported [`disabledProviders` setting](https://github.com/can1357/oh-my-pi/blob/v18.18.8/packages/coding-agent/src/config/model-settings.ts#L77-L82) and [capability filtering](https://github.com/can1357/oh-my-pi/blob/v18.18.8/packages/coding-agent/src/capability/index.ts#L360-L400); it does not merely hide MCP tool names. The tagged setting declares no environment override; the rebuilt environment also excludes `PI_CONFIG_FILES` and reserved `PI_*`/`OMP_*` capabilities. No live/global client settings are edited.

The native reviewer guard awaits `api.setActiveTools(["read","grep","glob"])` and verifies the exact active set before agent start and provider requests. CLI `--tools` alone is insufficient on the target runtime. A persistent `tool_call` hook also blocks every other tool **before approval/execution**. Blocked attempts remain in its nonce/job/source/PID-bound receipt and invalidate readiness, even if a later active-set readback is clean. The controller requires the actual scope receipt plus successful terminal model output. Its final reviewer text must be exactly one compact marker/JSON line, with no surrounding prose or code fence. Actual inherited MCP startup or instructions remain an isolation finding even with a clean tool roster.

The native **worker** guard (`src/update/worker-guard.ts`) is the same mechanism with a different allow-list: it awaits `api.setActiveTools` to the built-in `read, grep, glob, find, ast_grep, ast_edit, edit, write, bash, lsp, todo, wait, eval` that exist, reads the set back (extras fail the run; `read`, `edit`, `write` and `bash` are required) and gates every call. MCP, web, GitHub, subagent (`task`), memory and skill-management tools are denied, so untrusted upstream content cannot steer the owner's global MCP servers. A denied attempt is recorded in the worker's nonce/job/PID-bound receipt (`blocked`) for the reviewer, but does not by itself fail the port. The worker keeps its normal shell and edit power as the operator's OS user: path confinement is by instruction and review, not by the guard.

```sh
bun skills/dori-mode/scripts/src/cli.ts upstream check --config examples/update.config.json
bun skills/dori-mode/scripts/src/cli.ts upstream stage --config examples/update.config.json
bun skills/dori-mode/scripts/src/cli.ts upstream status --config examples/update.config.json
bun skills/dori-mode/scripts/src/cli.ts upstream watch --config examples/update.config.json
```

`check` observes exactly `remote` plus the full `ref`. A head equal to `baseUpstream` is unchanged. `stage` explicitly exercises the current exact head even when it is the baseline; its request receipt says `manual-current-head`, never a detected new commit. Both commands deduplicate an already attempted SHA, including failures and rejections. An unchanged head never spends another model run. `watch` is the same cycle with a configured interval and one controller lock for its lifetime. It stops on active or ambiguous work. Installation and normal boot start no updater.

Configuration is strict: `version:1`, `target:"dori"`, `runtime:"herdr"`, separate `root`/`localSource`, public credential-free HTTPS or a local Git `remote`, `ref:"refs/heads/..."`, an exact `baseUpstream` Git SHA, real `worker`/`reviewer` commands, optional `provision` commands and a nonempty `checks` command set. Every command has a unique `name` (letters, digits, `.`, `_`, `-`), nonempty `argv`, positive `timeoutMs`, and for provisioning/checks an optional candidate-relative `cwd`. `engine` is valid only on worker/reviewer; `modelAgentDir` accepts `~`. No shell string is constructed. All source preparation uses independent ordinary clones, no linked worktree or live-tree Git operation.

Every agent command must consume `{prompt}` or `{brief}`. `{candidate}`, `{job}`, `{agentConfig}` and `{sessions}` are also available per argv element. Worker and reviewer run in separate new processes with separate config/state/session/HOME/cache/tmp directories and contexts. Native OMP commands are rejected if they carry resume, continue, restore or fork flags; an `engine:"external"` wrapper is not inspected for them and owns its own fresh-context contract. Direct OMP invocation uses the actual CLI's `-p` pattern, `--no-session`, a dedicated `--session-dir` and native OMP `--config` overlay, `--no-title`, `--no-extensions`, `--no-skills`, `--no-rules`, `--no-context-files`, and `--wait-async`. The reviewer receives `--tools read,grep,glob`. Custom wrappers are trusted operator commands and must enforce equivalent fresh-context/read-only review behavior themselves. No automatic approval or credit/reset redemption is implemented.

Direct OMP commands are pinned to `--mode json`: the controller reads completed assistant `message_end` text only and requires a matching terminal `agent_end` plus successful process exit. User/tool content, streaming deltas, `turn_end` repeats and nonterminal ends cannot supply a verdict. The final message attests observed provider/model separately from the requested selector; a different observed exact provider/model holds the candidate. A wrapper's final plain-text marker is accepted only as the wrapper's trusted output contract.

`modelEnv` lists the exact host environment **names** a model client may inherit, such as `ANTHROPIC_API_KEY`. Their values are never in configuration, argv or receipts and are redacted from private child logs. Checks inherit none of these capabilities. By default the OMP agent directory is fresh too. An explicitly configured `modelAgentDir` is a trusted authentication/provider-settings reference outside source/staging, used only by model clients and never copied or snapshotted; it is never a session/state directory. Disabling discovery providers preserves this reference for model/auth resolution. Extra configured model/provider names alone do not establish session/state merging. `--no-session` and task-owned session paths keep normal session history separate; inherited MCP startup/instructions, writes to trusted/live client settings and credential copies remain disallowed. The native config overlay and Dori's generated `DORI_CONFIG` JSON are separate files.

Every launch rebuilds its environment: dedicated `HOME`, Dori config/state, harness home, XDG paths and tmp; a job-owned shared cache for frozen installs; and, for model agents, a native session directory and isolated `DORI_HERDR_SESSION`/`HC_SESSION`. Parent pane/workspace/session IDs and unrelated environment variables are absent. `DORI_RUNTIME=herdr`, `DORI_TELEMETRY=0` and `DO_NOT_TRACK=1` apply only to automated launches. Model authentication is an explicit trusted capability. This is environment/path isolation, **not an OS sandbox**: configured commands and model tools still run as the operator's OS user.

Runtime paths use a short per-command `/tmp/du-<identity>` symlink into the job's durable `runtime/ORDINAL` directory, so `HOME`, tmp, all XDG paths and native session/config paths remain short enough for Herdr/HC Unix sockets even under a deep staging root. Shared caches are reached through an owned link inside that directory; their actual data stays in the job. Each runtime's private `runtime-paths.json` binds its alias, real directory, cache, configuration hash and OS uid. Existing foreign paths, mismatched links or ownership receipts hold the launch without replacing them. The detector has the same mapping under `root/detector`.

`GIT_CEILING_DIRECTORIES` is the canonical real runtime directory: Git discovery from runtime tmp paths stops there, including through the short alias. Repositories deliberately initialized below that boundary remain discoverable.

These aliases and real runtime data are intentionally retained after exit or interruption: the controller cannot assume every descendant has stopped. `/tmp` aliases are not recovery snapshots or live activation links. After confirming **all** owned descendants have stopped, an operator may unlink only an alias whose uid and exact symlink target still match its retained ownership receipt; do not recursively remove its target or unrelated `/tmp` entries. Missing aliases can be recreated only from a matching ownership receipt; collisions require inspection. Recovery restores code/application data, not old runtime processes or their aliases.

Before model work the job freezes base-upstream, current local source (including dirty/untracked adaptations) and exact new upstream, with SHA-256 manifests and a union of changed paths. The existing local `omp-ulw.lock` and admitted `ref/omp-ulw/` code are an **opaque frozen dependency**, not ULW update targets: only these local pin files are copied into the independent incoming candidate before the worker starts. Every admitted library file remains in normal changed-path coverage, source/check/review binding and recovery. Manifests also bind explicit `ulwPresent` presence/absence (the directory coverage path is `ref/omp-ulw/`); an absent library must not be installed by a worker or check. A conflicting library already in new upstream holds staging rather than replacing or deleting it.
Source manifests record excluded nodes, and admission checks those exclusions before copying or executing source. A pinned base or incoming upstream may exclude **only real `.git` directories**. Any other excluded path holds preparation before the worker, including tracked `bin/dori`, upstream `node_modules`, `.omp`, runtime directories, other `ref` checkouts and private-key/environment filenames. Git ignore rules do not select source: ordinary dirty, untracked and ignored adaptations remain hashed, frozen and required in changed-path coverage.

The local input additionally permits real `node_modules` directories and a narrow non-source metadata boundary: root `config.json`; `.DS_Store`, `.env`, secret `.env.*`, `auth.json`, `credentials.json` and `.pem`/`.key`/`.p12`/`.pfx` files; and `auth`/`credentials` directories within the opaque `ref/omp-ulw` library. `.env.example` and `.env.sample` remain source. These credential/runtime inputs are never copied to the candidate or recovery source. Every other excluded local node holds preparation, including local `bin`, state/session/cache/tmp/evidence directories, other `ref` checkouts and opaque-library `bin`, `.cache`, `.omp` or global extension code. Keep runtime/application data outside the admitted source distribution; explicit application-data recovery is a separate input. The controller never silently drops those excluded code containers to finish a port.

Workers must not install dependencies or create `node_modules` directories at any depth; on entry to verification, before configured provisioning begins, candidate admission permits only real `.git` metadata. The controller alone owns dependency provisioning.

Candidate binding permits **only real `.git` and `node_modules` directories**, at the root or nested paths such as `ref/omp-ulw/.git` and `skills/dori-mode/scripts/node_modules`. These are exact path components, not prefix matches. Every other exclusion holds before/after trusted provision commands, at final source binding and after each check/review, even when the admitted-file hash is unchanged. Frozen-input checks and source snapshot/restore use the same admission boundary, so an excluded payload cannot disappear behind a successful hash comparison or recovery copy. Normal provision changes to admitted Dori source still precede the single final freeze; installed dependencies remain governed by trusted explicit provisioning.

Admitted source symlinks/special files fail rather than being followed; permitted Git/dependency metadata must itself be a real directory. This is a source admission boundary, not an embedded-secret scanner: keep source free of credentials. Neither the controller nor its worker investigates, ports, fetches or updates ULW.

The worker reconciles every changed path and emits a bound coverage receipt. It starts from incoming upstream rather than receiving a blanket old-source overlay. The controller then runs **every configured provisioning command** as trusted explicit preparation: frozen-lockfile installs for root, skill and extension, followed by the configured `bun run fmt` normalization in the example. Preparation may rewrite admitted Dori source, but frozen inputs, the opaque local ULW pin and Git metadata are enforced before and after every provision command, including failure. There is no automatic formatter, repair loop or retry.

The worker performs a three-way integration: it carries local edits and removals forward while integrating the delta from base to incoming upstream. Starting from an incoming checkout does not authorize restoring locally removed code or tests. In particular, removed wording, source-text, forwarding and incidental-default assertions are not missing behavior coverage to resurrect; consumer-visible behavior and boundary regressions remain required.

Only after all provisioning succeeds does the controller freeze and persist the final `sourceHash` and `ported-source.json`, then run **every configured check**. Provisioning receipts record actual preparation exits, not passed verification of that final hash. Check and review receipts must bind the final post-preparation source; any admitted-source mutation during a check or review holds the candidate rather than rebinding old evidence. All commands retain stdout/stderr/exit/time/process receipts. A fresh reviewer independently covers `upstreamCoverage`, `localAdaptations`, `correctness`, `isolation`, `verification`, `security`, `failureRecovery` and `scope`; its structured `DORI_UPDATE_REVIEW` response must bind the exact checked source, provide evidence for all eight items, findings and explicit limitations. Plain `VERDICT: CLEAR`, missing/malformed output, unavailable review, unknown items and stale source never grant readiness. Requested and observed model identities are separate receipt fields; unavailable observation stays `null`.

The **entire final assistant response** must be one physical line: `DORI_UPDATE_REVIEW ` followed by one compact JSON object, with no introduction, explanation, bullets, markdown fence or surrounding text. An approval requires all eight items to pass and `findings: []`. Any unresolved finding requires rejection; nonblocking observations belong in the relevant checklist evidence or limitations. The controller does not strip surrounding prose or reinterpret an invalid approval as readiness.

Private artifacts live in `root/jobs/JOB_ID/`: ordinary `candidate/`, frozen `inputs/`, `prepared-source.json`, `ported-source.json`, coverage/review briefs and receipts, per-command logs, generated `runtime/`, `job.json` and `report.json`. The report contains exact upstream/base/local/candidate hashes, actual check exits, independent verdict/limits, candidate path and rollback inputs. `ready` still means **candidate only**; automatic publication/deployment has a separate durable promotion record and never rewrites that readiness evidence. Candidate phases remain `prepared`, `porting`, `verifying`, `reviewing`, `ready`, `failed`, `rejected` and `interrupted`. The accepted upstream baseline advances in persisted state only after the configured complete promotion succeeds. Configuration identity stays bound to the root; changing policy requires a new staging root, not editing its historical baseline.

Stdout emits path-free JSON `DORI_UPDATE` events; detailed status and receipts remain private. For stage-only watching, the owning session's monitor tool can run `watch` and filter phase/candidate/held/error events so unchanged observations stay quiet. Automatic live replacement instead needs the external supervisor below: an in-session watcher dies with the session it replaces. Neither form posts periodic owner progress merely because a detection interval elapsed. `status` prints private local reports and must not be forwarded wholesale to a messenger.

Optional `reporter` is a trusted argv command consuming `{text}` (also allowed: `{job}`, `{upstream}`, `{phase}`). Its text is a fixed path-free JSON projection with hashes, check exits, verdict and limitation count; detailed findings remain in the local artifact. It can call existing `dori send slack|telegram|discord --to ... --text {text}` using the operator's actual target and trusted executable path. Set `reporterEnv` to exact messenger token/cookie names; only the reporter inherits them. No target/channel is built into product code. Sending intent is durable before the external write. A reporter that never started or exited nonzero is `failed`; one killed or lost after it started is `ambiguous` and `sending` after a crash becomes `ambiguous` on recovery. Neither is ever resent, neither changes the verdict, and neither blocks later updates; both appear in `status` and make `check`/`stage` exit 3.

### Recovery drill

Stop the watcher in its owning session first. Inspect retained process receipts and establish that all old children have stopped; the updater never guesses from an aged lock, kills an unknown PID or resumes an interrupted model/check. For an active job, `dori upstream recover --config FILE --ack-stopped ID` is the explicit acknowledgement. It clears active ownership and keeps the SHA deduplicated. A job that was still mid-run becomes `interrupted`; a job that already had a complete verdict (`ready`, `failed`, `rejected`) keeps it, and a `ready` verdict whose source no longer matches becomes `failed`. A live controller or foreign-host lock holds recovery.

Acknowledgement never retries or rebinds a terminal failed candidate. To evaluate a corrected controller against the same upstream SHA, use a separate configuration and a fresh isolated `root`, retaining the previous root and its receipts unchanged. This is a new run: it must perform a fresh port, every configured check and a fresh independent review; no archived check or verdict grants readiness. Never rewrite the old state's `configHash`, job phase or receipts.

If the watcher died while idle and there is no active job, `dori upstream recover --config FILE --ack-stopped none` acknowledges the stopped controller alone and retains its lock evidence in `recovery-ack.json`. Corrupt lock/state records require manual inspection; they are never guessed away.

The following commands discover the existing terminal job and create **fresh sibling directories**. Run them from the checkout with `jq` available; `config` is the existing example. First run the isolated candidate with its dedicated application data under `root/application`, then stop that candidate's state writers. `--app-state` must name that existing task-owned data, never the owner's live state or model-client directory. If skill `DORI_STATE_DIR` and harness `DORI_HOME` are separate, supply their common owned data container so both relative trees are preserved.

```sh
config="$PWD/examples/update.config.json"
root="$(dirname "$PWD")/dori-update-staging"
app_state="$root/application"
job="$(jq -r '.jobs | to_entries | last | .value' "$root/state.json")"
stamp="$(date +%s)"
snapshot="$(dirname "$PWD")/dori-source-state-$stamp"
restored="$(dirname "$PWD")/dori-restored-$stamp"
bun skills/dori-mode/scripts/src/cli.ts upstream snapshot --config "$config" --job "$job" --output "$snapshot" --app-state "$app_state"
bun skills/dori-mode/scripts/src/cli.ts upstream restore --config "$config" --input "$snapshot" --output "$restored"
jq '{phase, sourceHash, applicationStateHash, applicationState, candidateOnly}' "$restored/recovery.json"
```

`snapshot` requires no active/ambiguous updater work and freezes source, frozen inputs, updater control state and command receipts/logs. With explicit `--app-state`, it separately freezes actual application lane/paused state, receipts, monitor specifications, session identity metadata and inbound cursors. This state never enters source snapshots or model prompts. Application authentication, environment files, configuration/settings, private keys and personal client directories are excluded. No application state is inferred: omitting the flag records `applicationState:null` and produces a code/control-evidence snapshot only.

`restore` validates source, application-data and control/evidence manifests before writing a new destination: mutable `candidate/`, mutable `app-state/` when supplied, frozen `inputs/`, archived original control evidence and an explicit `interrupted` recovery record. It preserves application data bytes and statuses; it does not rewrite paused lanes, launch monitors or reconnect old processes. Point a new owned Dori config's `stateDir` and `DORI_HOME` at the restored relative trees before an explicit isolated restart. `applicationManifest()` exposes the admitted application-data hash for comparison, and the existing Registry/Store/cursor/monitor readers can read the restored data normally.

Restored historical checks/review grant no source readiness and are never loaded into the running watcher. Admitted opaque `ref/omp-ulw/` source and its presence/absence are restored with the code; installed packages, Git objects, model sessions/history and authentication are not. No existing source, live state or failed candidate is deleted or overwritten. State writers must remain stopped during a snapshot; changed inputs, links and special files fail rather than producing a misleading recovery copy. This is a source/application-data recovery procedure, not an OS image or an embedded-secret scanner.

Exit codes: `0` unchanged/ready or completed status/recovery, `3` failed/rejected/held candidate or failed reporter, `4` detector unavailable with proven stopped ownership (retryable), `2` configuration/operation error, `130` requested interruption. A timed-out detector is retryable only after its owned process group has stopped and both output pipes have drained; surviving or unproven descendants remain held. Before watcher activation, run `bun test ./test/update*.test.ts`, the repository checks, and a real explicitly configured `stage` cycle, then exercise the generated native guard and application-state restore on owned fixtures.

### Owner-authorized automatic publication and deployment

The optional `promotion.publish` object defines `remote`, full branch `ref`, `author: {name,email}` and, for GitHub, `github: {gh,credentialHome,requiredChecks}`. The remote must be credential-free. `gh` is the actual trusted executable, `credentialHome` references existing controller-only GitHub authentication in place, and `requiredChecks` lists the exact required check names. Local Git remotes support isolated real-Git proofs without a GitHub capability. Workers, reviewers and checks do not inherit publication credentials.

Publication derives its public manifest from the checked `ported-source.json`, verifies every exported byte and executable mode, and excludes the opaque `ref/omp-ulw` checkout. It never publishes the candidate's Git metadata, runtime state, model sessions or ignored private files. A separate own-repository commit preserves the exact expected main parent. The controller pushes an owned branch, opens or resumes its GitHub PR, requires successful checks for that exact commit, and only then fast-forwards the configured target. It never forces a ref. Concurrent target changes hold the job. Durable intent plus actual remote readback prevents a crash after push from repeating publication or model work.

When `reporter` is configured, promotion awaits a separate durable notice before pushing main and another before the first forward runtime stop. These are notifications, not approval requests. Accepted notices are reused only for the same job, action, exact publication/deployment intent, configuration and command receipt. A failed, unresolved or incomplete attempt holds the effect without automatically resending; terminal reports preserve the separate notice receipts. Without a configured reporter, existing non-notifying library operations remain unchanged.

Before new publication intent, the public frozen local tree must equal the observed target tree, so an owner commit cannot disappear beneath a newer manifest. Optional `publish.initialSource: {main,sourceHash,exportHash,baseUpstream,upstream}` authorizes one explicitly reviewed initial uncommitted source cutover. The exact main, reverified frozen local manifest, approved final public export and authentic upstream pair must all match. A durable job claim prevents reuse by another job; the publication record preserves its basis and pins for resume. It is not a concurrency or review override. Configure these pins before the state root's first use and never edit/remove them: configHash is write-once. After deployment changes local source, normal tree matching resumes without a config rewrite. Initial historical replay is labeled separately from a newly arrived upstream update. A confirmed published commit remains published when it is an ancestor of later main; deploying that older source holds rather than undoing owner work.

Initial-source publication tests share only a checked immutable export-hash reference; every scenario still prepares its own isolated candidate and receipts. Pass the existing shared reference to bootstrap fixtures instead of repeating reference-only Git preparation inside each case's execution deadline.

Terminal held promotions retain their evidence and baseline but do not block detection of newer upstream SHAs. Pre-record tree, pin and one-time-claim mismatches are durable terminal holds, not silent publishing retries. The same attempted SHA remains deduplicated and is not silently re-ported. Retryable busy/pre-stop preparation/lock holds do not consume the terminal failure notification. GitHub's stale `blocked` mergeability after successful exact-head checks remains waiting, not approval. CI waiting retains its first deadline: the configured check timeout sum, bounded to 1–24 hours. Missing evidence or unresolved mergeability at that deadline becomes a terminal hold with one notification.

An owner commit on main, publish-only operation or rollback after successful publication can leave localSource behind main. The normal guard then holds until an operator reconciles source. Prepare an owned checkout of the actual target commit, retain the admitted opaque local ULW pin unchanged, inspect the owner delta and verify that source, then retarget the already-configured stable localSource link. Never rewrite configHash, baseline, old job evidence or publication receipts to bypass the guard. Admission runs at publication time after ready, so an unreconciled source can spend one doomed port per newer upstream SHA; same-SHA dedup still applies.

`promotion.deployment` is optional and currently requires Linux process identity support. Its explicit config identifies `releaseRoot`, stable `liveSource`, operator `home`, `doriHome`, `doriConfig`, `stateDir`, private `bun`, native `omp`, `herdr`, `pane`, `sessionId`, `model`, shared `restartLock`, fixed `launcherPath` and bounded `healthTimeoutMs`. Optional `stopTimeoutMs`, `herdrSession`, `monitorBootstrapFile`, `quiesceCheckpointFile` and release-relative `shims` cover the operator's actual runtime. For initial real-directory conversion only, `legacyOmp` can preserve a different old native runtime; it must hash-match the captured running executable. Later managed rollbacks use the prior release's recorded toolchain, not this legacy path. The pane/session/state directory must describe the same owning Dori, not an arbitrary foreground command.

The deployment transaction verifies and prepares the committed managed release before touching the live source. A legacy real source directory is preserved by rename, not deleted. It journals the old pointers and exact PID/start/boot/session identities before stopping anything, switches only configured links, and resumes the same native session by reference. Existing application state, paused goals, cursors, credentials, model history and global model policy stay in place; they are not copied into a release. New health requires the correct role/session/PID/code, desired monitor descendants and fresh intake heartbeat. Process existence or a printed success string is insufficient.

Managed startup, rollback and restart bind the actual private OMP entrypoint, native version, Bun bytes and an owned per-process `{"update":{"auto":false}}` overlay. Private Bun/OMP directories precede trusted operator CLI directories in the actor's explicit PATH. Existing global native/Bun installations and model settings are not rewritten. A first legacy rollback uses its separately verified old native receipt; a newer installed global binary is not evidence of the running actor's version.

`launcherPath` is the operator's stable restart executable slot, for example `~/.dori/bin/managed-native-restart`. The transaction preserves that slot and switches it to an owned script pinned to the prepared controller release. Do not point this field at a controller `.ts` source file or at the outer delay/model-watch wrapper. Before first conversion, a protected initial delegate may invoke `bun FIXED_CONTROLLER/src/update/deployment-launcher.ts DEPLOYMENT_CONFIG_JSON`; the outer helper delegates to the stable slot before any signal.

Ordinary replacement/restart holds busy or approval-blocked actors. An initial self-handoff may use a private, expiring, exact-intent/commit/source/PID-bound quiesce checkpoint; it is not a reusable busy override, and approvals still block it. A trusted first-boot monitor bootstrap supplies `{version:1,sessionId,monitors:[{name,argv,filter,cwd}],intake:{path,monitor,maxAgeMs}}` and optional recorded running monitor PIDs. The controller revalidates ownership before cleanup. New persisted starts remain compatible with legacy rollback. Token-loading monitors must load their own credentials inside protected child launchers, not inherit a token or sudo password from the resumed Dori.

Script-based monitors can share the native actor's foreground group. Only managed deployment may disregard their exact attested processes: the native actor must be present in its actual foreground group, and each ignored monitor must match its desired command/cwd and saved incarnation as that actor's descendant. Initial bootstrap needs a `runtime` receipt with `pid,startTicks,bootId,executable,imageDev,imageIno,pane,role,sessionId,startedAt`, plus each `running` entry's complete `identity` (`pid,startTicks,bootId,executable,imageDev,imageIno`). Thin `{name,pid}` entries alone do not grant this exception. Managed actors use their current owned runtime-health record and persisted monitor specs, including monitor start ticks. Unknown shells, a foreground root shell, stale/reused/foreign identities and missing proof still hold. Generic harness delivery and its foreground-shell rules are unchanged.

Launch identification and failed-start cleanup use the same strong foreground attestation for managed actors, including a prior managed rollback. A matching live but unattested process is a hold, not evidence that no process launched. Starting or resuming a launch requires a positively identified bare pane-root shell with no live pane owner or children, including background or suspended descendants; a native actor's Bash monitors never satisfy that condition. Unknown metadata and unsupported shell flags hold rather than typing a second launch into an existing process. The pre-role, no-shell startup cleanup path remains bound to its exact journaled executable, argv and chronology, and initialized actors must be idle without approval before cleanup.

A shell alias is admitted only when its absolute kernel argv0 resolves to the observed executable and the reported shell name remains bound to that argv0, for example `/bin/sh` resolving to `/usr/bin/dash`. A matching display name without exact canonical image and incarnation proof is insufficient.

An initial legacy rollback may have no runtime-health writer. Only the controller's journaled rollback launch and health observation may then bind the new native incarnation to the preserved monitor commands, actual working directories and current descendant identities. This separate rollback proof does not rewrite the original bootstrap or authorize another launch. Unknown shells and changed incarnations still hold. Native `ps` observations use the observer's resolved time zone, so a caller's different `TZ` does not alter process-start chronology or relax its time window.

Failed-start rollback discovery and its pre-signal safety attestation retry fresh observations within bounded windows, so an exiting monitor child cannot turn one transient snapshot into an immediate terminal rollback failure. Each attempt still enforces the exact process, image, argv, chronology, session, idle and approval guards; deadline or cancellation never authorizes signalling an unverified process. Observing a completed bootstrap rollback is read-only and requires the genuine `rolled-back`/`done` journal, `rollbackHealthyAt`, matching rollback process/runtime and original source proof, and the unchanged bootstrap with current monitor incarnations. This completed observation grants no launch capability and never rewrites the journal step or original bootstrap.

Re-entering a completed rollback only waits for fresh bounded health to match its saved runtime receipt. It does not change `done`, persist the record again, restore pointers, signal or launch another process. Live replacement and kernel-bound cleanup require Linux `/proc` and pidfds; other platforms hold before native effects, while portable detection, publication, pointer and admission checks remain enabled. Pointer backups preserve the symlink inode itself rather than following its target on Linux and macOS, including dangling links.

Herdr `done` is admitted as idle-equivalent only when process-bound native metadata does not attest `working`. Native working metadata remains authoritative and requires ordinary idle convergence or the exact one-shot quiesce checkpoint. Approval and identity guards still apply. Pre-stop command/lock failures get one persisted 1-hour failure-retry window; expiry is a terminal hold without signalling the actor. Verified busy waits do not consume that failure window. Malformed source, integrity failures and post-stop ambiguity do not acquire retry permission.

The intake heartbeat is a decimal epoch-millisecond timestamp written by the configured intake monitor. It must be an owned regular file without group/world write permission; use mode `0600`, including for an existing receipt. A live process and a fresh but group-writable pulse do not satisfy deployment health.

On failed startup or health, rollback restores the prior execution source and session when that can be done without interrupting new owner work or approvals. An ambiguous identity or newly busy actor holds for inspection instead. Runtime rollback does not rewrite published GitHub history: main and the running release can temporarily differ, and the promotion record distinguishes them. `dori upstream restart --config FILE` uses the configured managed restart lock and the same identity/health checks; existing model-watch helpers must delegate before sending any signal.

### Resident supervision

Run `scripts/update-supervisor.ts --config FILE --controller DIRECTORY --bun EXECUTABLE` outside the Dori it may replace. The controller directory is a stable link to the accepted controller release; each cycle invokes the actual `upstream check`, so the next cycle loads accepted code. When the link changes, the supervisor exits for the service manager to reload itself. It uses `intervalSeconds` from the config, does not manufacture status messages, and never retries a model merely because the interval elapsed. Completed detector unavailability (exit `4`) waits for the next interval rather than disabling the service; configuration errors still stop it. Unfinished ambiguous model work remains held; only finished ready promotion effects have automatic readback-based recovery.

On Linux, `SIGUSR1` wakes the supervisor's next check without interrupting an active cycle. An expiring initial quiesce checkpoint can therefore be consumed immediately rather than waiting a full polling interval. The signal does not bypass deployment, publication or review gates.

[`examples/update-supervisor.service`](../../../examples/update-supervisor.service) supplies an outside-session systemd user unit for the layout `~/.dori/update/{config.json,controller}` and `~/.dori/toolchains/bun-1.4.4/bun`. Provision that private Bun and the trusted controller link explicitly, configure publication/runtime identities and protected monitor launchers, and install the unit as `~/.config/systemd/user/dori-upstream-update.service` before `systemctl --user enable --now dori-upstream-update.service`. This does not upgrade global Bun. Exclude generated releases/toolchains/jobs from unrelated home-backup source tracking. Systemd supervision does not silently recreate an unavailable unrelated herdr server.

Use only trusted upstream and configured commands: source/process/environment separation is not an OS sandbox. First exercise a real nonempty upstream delta, exact-source checks/fresh review, publication readback, native restart, monitor/intake continuity and failed-start rollback in owned fixtures. If replaying an authentic historical change because upstream has no new revision, report that fact; an unchanged-head `stage` is not evidence that a new update was automatically ported.
